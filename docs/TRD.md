## 2. 기술 스택과 선택 이유

| 기술 | 역할 | 고른 이유 (한 줄) |
|------|------|-------------------|
| Next.js (App Router) | 화면 + API 서버 | 화면과 API를 한 프로젝트 안에서 같이 만들 수 있어서, 서버를 따로 세우지 않아도 된다. |
| TypeScript | 개발 언어 | 변수에 "이건 문자열, 이건 true/false" 같은 타입을 적어 두면 실수를 실행 전에 잡아 준다. |
| React (Next.js에 포함) | 화면 구성 | 체크박스를 누르면 화면이 바로 바뀌는 것처럼, 데이터가 바뀌면 화면을 자동으로 다시 그려 준다. |
| Jest | 테스트 실행 | "이 함수에 이걸 넣으면 이게 나와야 한다"를 코드로 적어 두고 자동으로 확인할 수 있다. |
| Testing Library | 화면 테스트 | 사용자가 실제로 하는 것처럼 "입력하고 버튼 누르기"를 흉내 내서 화면을 검사할 수 있다. |
| MySQL | 데이터 영구 저장 (v0.3부터) | 널리 쓰이는 무료 DB라 자료가 많고, 서버를 껐다 켜도 데이터가 남는다. |

## 3. 폴더 구조와 역할

| 폴더 | 들어가는 것 | 예시 |
|------|-------------|------|
| app/ | 페이지와 API 라우트 | 메인 페이지, 할 일 API |
| src/components/ | 화면 컴포넌트 | 입력 폼, 할 일 목록, 할 일 한 줄 |
| src/lib/ | 서버 로직, DB 접근 | 제목 검사, 저장/조회/삭제 함수 |
| src/types/ | 화면과 서버가 같이 쓰는 타입 | 할 일(Todo) 타입 |
| docs/ | 명세 문서 | PRD, TRD 등 |

역할을 나누는 이유: 화면(components), 요청 받기(app/api), 실제 처리(lib)를 나눠 두면, DB를 바꿀 때 lib만 고치면 된다.

## 4. 시스템 구성

```
[브라우저]                         [Next.js 서버]
 화면 컴포넌트  ──HTTP 요청──▶  API 라우트 (app/)
 (src/components)                     │
        ▲                             ▼
        │                       서버 로직 (src/lib)
        └──────HTTP 응답────          │
                                      ▼
                                 저장소 (버전별로 다름)
```

### 버전별 저장소

| 버전 | 저장 위치 | 화면 → 저장소 연결 방식 |
|------|-----------|--------------------------|
| v0.1 | 브라우저 메모리 (React 상태) | API 없이 화면 안에서만 처리 |
| v0.2 | 서버 메모리 (src/lib 안의 배열) | 화면 → API → lib → 서버 메모리 |
| v0.3 | MySQL | 화면 → API → lib → MySQL |
| v1.0 | MySQL (배포 환경) | v0.3과 같음 |

v0.2 → v0.3으로 갈 때는 src/lib의 저장 부분만 바꾸고, 화면과 API는 그대로 두는 것을 목표로 한다.

### MySQL 연결

- MySQL에 접속하는 코드는 src/lib에만 둔다. 화면(components)은 MySQL을 직접 모른다.
- 접속 정보(주소, 사용자, 비밀번호, DB 이름)는 코드에 적지 않고 환경 변수(`.env.local`)에 둔다. 이 파일은 git에 올리지 않는다.
- 테이블 구조는 docs/DATA_MODEL.md를 따른다.

## 5. 흐름: "추가" 버튼을 누른 뒤 DB에 저장되기까지 (v0.3 기준)

요청·응답의 자세한 형식은 docs/API_SPEC.md에서 정의한다. 아래는 6장의 API 규칙을 따른다.

1. **사용자 입력**: 사용자가 입력창에 제목을 적고 "추가" 버튼을 누른다.
2. **화면에서 1차 검사**: 화면 컴포넌트가 앞뒤 공백을 지운 제목이 1~100자인지 확인한다. 조건에 맞지 않으면 서버로 보내지 않고 화면에 안내를 보여준다. (빠른 피드백용)
3. **요청 보내기**: 화면이 서버로 요청을 보낸다. `POST /api/todos`, 본문 `{ "title": "우유 사기" }`
4. **API가 요청 받기**: app/ 아래의 API 라우트가 요청을 받아 본문에서 제목을 꺼낸다.
5. **서버에서 2차 검사**: 서버가 제목의 앞뒤 공백을 지우고 1~100자인지 다시 확인한다. 화면 검사는 우회될 수 있으므로 서버 검사가 최종 기준이다. 틀리면 `400` 오류 응답을 보내고 끝낸다.
6. **서버 로직 호출**: API 라우트가 src/lib의 "할 일 추가" 함수를 부른다.
7. **할 일 만들기**: lib 함수가 새 할 일을 만든다. 고유 id(UUID), 공백을 지운 제목, 완료 여부(false), 만든 시각을 채운다. (필드는 DATA_MODEL.md)
8. **MySQL에 저장**: lib 함수가 MySQL의 `todos` 테이블에 새 할 일을 넣는다(INSERT).
9. **응답 보내기**: 저장이 끝나면 API가 `201`과 함께 만들어진 할 일 JSON을 돌려준다.
10. **화면 갱신**: 화면이 응답받은 할 일을 목록 맨 위에 넣는다(최신순). 입력창을 비운다.
11. **실패 시**: 서버가 오류를 돌려주면 목록은 그대로 두고, 오류 응답의 `message`를 화면에 보여준다.

새로고침하면 화면이 목록 조회 요청(`GET /api/todos`)을 보내고, 서버가 MySQL에서 최신순으로 읽어 돌려준다. 그래서 데이터가 유지된다(F-05).

완료 전환(F-03)과 삭제(F-04)도 같은 길을 지난다. 체크박스나 삭제 버튼에서 시작하고, 7~8단계가 "완료 여부 바꾸기(UPDATE)"나 "삭제(DELETE)"로 바뀐다.

## 6. API 규칙

| 항목 | 규칙 |
|------|------|
| 주소 | 목록·추가는 `/api/todos`, 전환·삭제는 `/api/todos/{id}` |
| 제목 공백 | 서버가 앞뒤 공백을 지운 뒤 1~100자인지 검사한다. 공백만 있으면 빈 제목으로 보고 `400` |
| 성공 응답 | 감싸지 않고 그대로 보낸다. 목록은 배열 `[...]`, 할 일 하나는 객체 `{...}` |
| 오류 응답 | `{ "error": { "code": "...", "message": "..." } }` 형식. `code`는 테스트에서 확인하고, `message`는 화면에 보여준다 |
| 완료 전환 | `PATCH /api/todos/{id}`에 `{ "completed": true }`처럼 바꿀 값을 보낸다. `completed` 외의 값은 받지 않는다(수정 기능은 범위 밖) |
| 삭제 | `DELETE /api/todos/{id}`. 성공하면 `204`(응답 본문 없음) |
| 없는 id | 없는 id나 형식이 틀린 id로 전환·삭제하면 `404` |
| 정렬 | `created_at` 내림차순. 같으면 `id` 순서로 정렬해 항상 같은 순서가 나오게 한다 |

## 7. 기능별 기술 처리

| 기능 | 처리 방식 |
|------|-----------|
| F-01 할 일 추가 | 앞뒤 공백을 지운 뒤 화면과 서버 양쪽에서 1~100자 검사. 서버 검사가 최종 기준 |
| F-02 목록 보기 | `created_at` 최신순, 같으면 `id` 순. 정렬은 서버(lib)에서 한다 |
| F-03 완료/미완료 전환 | id로 할 일을 찾아 요청받은 `completed` 값으로 바꾼다 |
| F-04 삭제 | id로 할 일을 찾아 지운다 |
| F-05 데이터 유지 | v0.2는 서버 메모리, v0.3부터 MySQL에 저장 |

## 8. 개발 규칙 (CLAUDE.md 요약)

- any 타입 금지. 화면과 서버가 같이 쓰는 타입은 src/types에 둔다.
- 한 번에 한 기능만 작업한다.
- 테스트를 삭제하거나 skip하지 않는다. 실패하면 구현을 고친다.
- console.log는 디버깅 후 지운다.
- 주석은 한국어로 짧게 쓴다.

## 9. 테스트 전략

| 대상 | 도구 | 무엇을 확인하나 |
|------|------|-----------------|
| src/lib 함수 | Jest | 제목 검사(공백 처리 포함), 추가/조회/전환/삭제 결과, 최신순 정렬 |
| API 라우트 | Jest | 올바른 요청과 잘못된 요청에 맞는 상태 코드와 오류 `code` |
| 화면 컴포넌트 | Jest + Testing Library | 입력 → 버튼 → 목록 반영, 체크박스, 삭제 |

테스트 실행: `npm test`
